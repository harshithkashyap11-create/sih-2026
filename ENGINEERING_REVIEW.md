# Pre-production engineering review — 16 September 2026

**Release decision: NOT READY for public production with real patient data.** The implemented workflows are substantially stronger and tested, but offline privacy, private-media reliability, API contracts, content review, and operational setup remain release gates. A test deployment with synthetic data is appropriate after configuring the services below. The executable checks and sign-off worksheets are in [docs/release-gates.md](docs/release-gates.md).

## Scope and architecture

The implemented project is `SMARANA/`; the sibling `smarana-kit/` contains the original starter specifications. The existing Django/DRF, PostgreSQL, Celery/Redis, S3/MinIO, React/TypeScript, Dexie outbox, and PWA architecture was retained. Review traced authentication, role/assignment boundaries, routines and prescriptions, game metrics and difficulty, memories and quiz attempts, caregiver check-ins, emergency alerts, offline replay, and PDF exports. Configuration, CI, database migrations, tests, and deployment files were inspected. This is a source and local runtime review, not a penetration test or a complete production infrastructure certification.

## Remaining issues and incomplete features

1. **High: offline data protection.** [frontend/src/db/schema.ts](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/frontend/src/db/schema.ts>) caches patient profiles, family contacts, memories, medications, and logs in plaintext IndexedDB. `db/crypto.ts` encrypts only the refresh token using a four-digit PIN; an attacker who copies the browser database can bypass the UI lockout and enumerate PINs. Account scoping protects normal UI use, not physical device compromise or same-origin malicious script. A privacy-reviewed encrypted storage design and shared-device data retention/erasure policy are required before real patient data. Encryption must preserve unsynced outbox writes; blindly clearing storage would lose records.
2. **High: private media is not production-offline complete.** [frontend/vite.config.ts](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/frontend/vite.config.ts>) caches `/media/`, whereas S3 keys are `memories/...` and `family/...`. Signed URLs expire after ten minutes, while [backend/apps/sync/pull.py](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/backend/apps/sync/pull.py>) sends unchanged memories/family only incrementally and frontend repositories may indefinitely reuse those cached links. A stable authenticated media identity, refresh strategy, patient-scoped offline blob store, and real S3 offline/expiry tests are needed. Local filesystem and bundled practice tests do not validate this integration. Do not make the bucket public as a workaround.
3. **Release gate: localization and cultural material.** [frontend/src/shared/i18n/as.json](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/frontend/src/shared/i18n/as.json>) and `bn.json` contain 298 TODO-marked lines combined; catalog checks verify matching keys, not finished translations. [frontend/src/content/packs.ts](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/frontend/src/content/packs.ts>) silently falls back to bundled generic English demonstration packs. Native-speaker/content-owner review is required; these are not complete curated regional packs.
4. **Release gate: strict backend typing/CI.** The existing CI `mypy --strict` services step reports 88 errors in 21 files, including missing typed framework integration, Any returns/decorators, and model/type definitions. Add compatible Django/DRF stubs/plugins and correct annotations; do not disable the check or claim CI is green. The number was measured during this review, before the last additions.
5. **Important: incomplete OpenAPI contracts.** [backend/schema.yml](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/backend/schema.yml>) and generated frontend API cover only part of the current product. Many APIViews in clinical, memories, reports, sync, alerts, games, and voice lack complete request/response declarations. Generation reports 179 errors (35 unique) and 10 warnings (7 unique), despite producing a file. New JWT auth scheme registration is fixed. Full `check --deploy --fail-level WARNING` still fails on schema diagnostics; the separate security-tag check passes. Finish explicit operation/serializer contracts and regenerate the client/schema before API consumers rely on them.
6. **Important: clinical UI coverage.** [frontend/src/features/doctor/PatientTabs.tsx](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/frontend/src/features/doctor/PatientTabs.tsx>) still has no full prescription edit/deactivate UI, assignment edit/deactivate UI, or assessment-score editor even though backend update endpoints exist. Some lists need clearer empty states. Patient-visible clinical notes do not have a complete patient reading workflow in the router.
7. **Incomplete external channels/content.** Push and SMS are explicitly disabled in notification preferences; video/audio memory models exist but uploads currently accept photos. Optional voice fallback requires a configured provider and was not live-tested. Web Speech behavior varies by device/language and needs real Android testing.
8. **Reliability: notifications are at least once.** A mail server can accept an email before the app records its delivery; a crash may cause a duplicate retry. Current retries cover recent open urgent alerts; this is not a durable per-recipient delivery queue with provider receipts/escalation. Do not present SOS email as guaranteed emergency dispatch. SMTP still runs within alert transactions, bounded by the production timeout; move delivery to a durable transactional outbox for higher scale.
9. **Database/API hardening.** User email/phone identities are not uniquely constrained (`accounts/models.py`), while professional login selects the first matching record. Define normalization/identity uniqueness and resolve duplicates before adding constraints. Review missing indexes for growing patient/date event tables and add bounded pagination to currently unbounded session/note/history/snapshot endpoints. Do not add unsafe uniqueness migrations without examining existing production data.
10. **Performance.** Final build reports a main bundle around 1.3 MB before gzip and a practice-asset precache around 10 MB. Lazy-load role portals/game modules and replace blanket practice-pack precaching with selected-region downloads. Some serializers perform per-row queries (assignment completion, alert forwarding eligibility). Measure query counts and latency on representative histories.
11. **Security/operations.** Add trusted-ingress rate limits; DRF cache throttles are not an atomic brute-force protection. Add a tested CSP, log redaction/retention, secrets rotation, audit access restrictions, device-loss revocation, and a privacy/security review. No operational alerting, restore exercise, database PITR policy, or worker-liveness monitoring was provisioned here.
12. **Reproducibility.** Backend requirements and container tags remain ranged/unpinned; build and audit a pinned release dependency set and image digests. Development Compose still uses runserver/Vite, default credentials, and local MinIO; it is not the release deployment.

## Exact deployment sequence (after release gates are resolved)

1. Resolve the real-data release gates above; approve language/content and privacy behavior. Choose staging and production domains and an owner for alerts/recovery. Use synthetic data in staging.
2. Provision supported PostgreSQL with TLS, a restricted application role, automated backups/PITR and a tested restore; private Redis; private S3-compatible storage with least-privilege application credentials, versioning and restricted CORS; verified SMTP sender. Configure monitoring for HTTP errors, database health, worker/beat liveness, failed mail, and rejected sync records. Record recovery objectives and escalation contacts.
3. In the project root, copy [.env.production.example](</home/harshithkashyap/Downloads/smarana-kit (1)/SMARANA/.env.production.example>) to `.env.production`. Fill every blank from the deployment secret manager. Generate an independent random signing key of at least 50 characters. Set exact hosts/origins, secure database connectivity, real storage endpoint, and SMTP credentials. Restrict file permissions (`chmod 600 .env.production`). Never seed demo accounts or copy `.local/` into production.
4. Configure an HTTPS ingress to forward to `127.0.0.1:8080`, preserve Host, and **overwrite**, not append, `X-Forwarded-Proto`. Keep port 8000, database, Redis and storage administration private. Enable `DJANGO_TRUST_PROXY=true` only with that trusted ingress. Obtain/renew TLS certificates. Verify all affected subdomains support HTTPS before enabling HSTS subdomain/preload policy.
5. From `SMARANA/`, build the release: `docker compose -f docker-compose.prod.yml build`. Tag/store immutable image versions. Verify the release artifact uses the reviewed lockfile. This must be tested in staging; the new container path has only been configuration-validated locally.
6. Take a database backup before release. Run `docker compose -f docker-compose.prod.yml run --rm migrate` to apply migrations and collect Django static files into the shared volume. The bootstrap service must succeed before starting the application. Run it once per release, not independently from each worker.
7. Create the real administrator: `docker compose -f docker-compose.prod.yml run --rm backend python manage.py createsuperuser --role admin`. Verify password + CSRF login as an active staff user with the Admin role, retain a controlled recovery procedure, and do not use the historical django-otp records as a release requirement; the current shipped admin policy intentionally removes OTP enrollment and management.
8. Start services: `docker compose -f docker-compose.prod.yml up -d backend celery celery-beat frontend`. Run exactly one beat instance. Verify container health and logs. Check `docker compose -f docker-compose.prod.yml exec backend python manage.py check --deploy --tag security --fail-level WARNING`. Once schema declarations are fixed, require the unrestricted deployment check too.
9. Before admitting users, test the public HTTPS URL: redirects, certificate, secure cookies, admin MFA, each role, unassigned-patient denial, expired-access refresh, multi-device sessions, prescription change/stop, doctor assignment/review expiry, real image upload/signed URL expiry, offline reload/unlock/sync/replay, new/repeated SOS, SMTP failure/retry, and PDF visibility. Confirm no demo accounts or public media bucket exists.
10. Run `scripts/backup-production.sh`, restore its database dump into an isolated target with `scripts/restore-production.sh`, and verify the object mirror and SHA-256 manifest. Capture baseline latency/query counts, run a concurrency/load test, and confirm operational alerts reach owners. Record a rollback image and schema-compatible rollback plan; stop writes before any destructive recovery. Promote only after every release gate is signed off.
